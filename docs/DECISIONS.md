the full reasoning lives there. This file mirrors their status and records internal choices made while building
(`P<n>-D<k>: choice / reason / risk`). Changing an ADOPTED project decision needs a DECISION REQUEST.

## Internal decisions
- P0-D1: n1, n2 limited to 0..10 / the largest DC magnitude of a level-shifted 8x8 block is 1024 = 2^10, so larger steps only zero every block / none.
- P0-D2: Gradle 9.9.0 wrapper, JUnit 5.11.4 BOM, jar name fixed to `layer-codec.jar` / launchers never change / none.
- P0-D3: Launchers pick Java as LAYER_CODEC_JAVA, then `java_home -v 21`, then JAVA_HOME, then PATH; heap -Xmx4g / the Mac default `java` was 20, which cannot run Java 21 bytecode / Windows launcher relies on JAVA_HOME or PATH.
- P0-D4: `vendorJunit` task copies the JUnit console jar to `build-tools/` / the build sandbox cannot reach Maven Central / two ways to run tests; Gradle on the Mac stays the authority.
- P0-D5: Naive baseline overlay will be regenerated in Java (`VizSeg --naive`, P1) as the fair same-code comparison; the PM prototype image is kept at `docs/img/naive_probe_overlay.jpg` and its script at `tools/prototype/probe_motion.py` for reference (moved from the repo root Nov 10) / same-code comparison is fairer / none.
- P0-D6: Rotation read from display-matrix side data `rotation` (counter-clockwise) first, legacy `TAG:rotate` (clockwise) as fallback; ffprobe output parsed as `-show_streams` key=value / FFmpeg 5+ dropped the tag and 4.4 (sandbox) vs 7.1 (Mac) name sections differently / a clip with a non-multiple-of-90 rotation is rejected with a clear error.
- P0-D7: Frame planes are `int[]` (0..255), not `short[]` / no casts in inner loops; 25 MB per padded 1080p frame and only about 3 frames are held / memory, acceptable.
- P0-D8: Display scales frames itself (integer bilinear, rows in parallel) into a screen-sized image and draws it 1:1 / Java2D scaling of an image written through its raster measured 48 ms per 1080p frame on the Mac (SAL 20.83 s for a 14.57 s clip, 100% late); our scaler measured 1.8 ms per frame in the sandbox / bilinear at 0.72 slightly softens fine detail, so judging compression artifacts needs the 1:1 zoom toggle planned in D8.
- P0-D9: Types.java interface (Frame int planes, VideoInfo, MotionField short dx/dy with D12 convention, Labels byte ids) APPROVED by Dhruvin Nov 10 / every later part builds on it / changes now need a DECISION REQUEST.
- P1-D1: Full search tie-break: lowest SAD, then smallest |dx|+|dy|, then first in scan order (dy then dx ascending); (0,0) is the starting best / flat or ambiguous blocks report (0,0) instead of an arbitrary offset, and output is deterministic / a block that truly moved over a flat area reports (0,0), which reliability (P1.4) marks unreliable anyway.
- P1-D2: Search window clamped so the reference block stays inside the padded frame; no out-of-frame candidates / no invented pixels, matches the oracle exactly / edge blocks see a smaller window, so motion leaving the frame can be missed at the border.
- P1-D3: SAD computed with an early exit once the running sum is strictly greater than the current best (checked per row) / same answer as a full SAD, about 3x faster on real clips / none; the oracle test compares against a version with no early exit.
- P1-D4: Thresholds live in `codec.common.Config` as one record per module (`Config.Motion` first) / one file to tune and to copy into RESULTS.md / none.
- P2-D1: [B/P2] DCT is orthonormal DCT-II (class formula, C(0) = 1/sqrt2), separable with a precomputed cosine table, level shift 128 inside `Dct`; coefficients stored row-major `coef[v*8+u]` (v vertical, u horizontal), no zigzag / matches the brief's natural order and JPEG convention; forward then inverse is exact to 1e-9 / none.
- P2-D2: [B/P2] `Dct.inverse` returns unrounded doubles with the level shift added back; rounding and clamping to 0..255 happen in Quant (P2.2) / keeps the DCT testable as lossless and puts every lossy step in one place / none.
- P2-D3: [B/P2] Decoder uses `Dct.inverseZeroSkip` (skips all-zero coefficient rows), proven bit-identical to `Dct.inverse` on 500 sparse blocks / quantized blocks are mostly zero rows, and serial 1080p decode is over budget (P0 speed gate) / speedup to be measured on the Mac in P2.9.
- P2-D4: [B/P2] Quantization q = round(c / 2^n) half away from zero, stored as short, overflow throws; dequant q * 2^n; pixels after IDCT rounded half up and clamped 0..255 in `Quant.toPixel` / symmetric rounding treats negatives like positives and halves the mean error vs truncation (tested ratio 0.45..0.55) / none.
- P2-D5: [B/P2] `Zio`: Deflater level 1, Deflater/Inflater created per call and always end()ed in finally, loops until finished(), inflate requires the exact expected length (from the frame header) and reports truncated / too long / corrupt as IOException / native memory is invisible to GC, one call may not drain the stream, and a known output size turns silent corruption into a clear error / per-call native allocation, negligible next to a 12.6 MB frame.
- P2-D6: [B/P2] .cmp v1 implemented exactly to 03 D7 in `CmpFormat` (Header record, Writer, Reader, blockTypes, encode/decodeBaseline). Writer streams and writes frame count 0 and footer offset 0 first, patching both at close, so a crashed encode is detected as unfinished. Reader uses positional FileChannel reads only (thread-safe for P3), checks every frame slot against the next offset, and knows only mode 0 for now (P4 adds its mode). In memory: `byte[] types` per 8x8 block and `short[] coef` 192 per block (R, G, B) / one place owns the byte layout; every corruption gives a clear CmpException / none.
- P2-D7: [B/P2] `DecodeCore` writes only pixels inside the true width/height, so decode and crop are one pass; per-thread `Scratch`, no static mutable state; `decodeParallel` splits one frame by 8x8 block rows (disjoint writes, bit-identical to serial, tested) for the P2.9 all-cores measurement, while P3 will parallelize across frames / skips a 25 MB padded copy per 1080p frame and keeps P3's options open / none.
- P2-D8: [B/P2] `FrameEncoder` (approved by PM Nov 11): frame (true size or padded) + macroblock Labels in, raw baseline payload out; pads, derives block_type, DCT per channel, quantizes by type; serial and block-row parallel versions are byte-identical (tested). No segmentation logic / EncoderMain and CodecHarness share one tested path / none.
- P2-D9: [B/P2] `Psnr`: error summed over R, G, B; a pixel's layer is its 8x8 block_type; reports mean of per-frame PSNR (primary) and pooled PSNR; zero error capped at 99 dB, absent layer NaN / standard definition, per-layer as D10 requires / mean-of-frames vs pooled differ slightly, both printed.
- P2-D10: [B/P2] `CmpFormat.Reader` gains read-only `offset(k)` and `lengths(k)` for CmpDump's frame table; byte layout unchanged (v1 stays frozen) / the dump shows the grader where every frame lives / none.

## [C/P3]
- P3-D1: Decode is frame-parallel: each worker decodes whole frames with the SERIAL `DecodeCore.decode` and its own Scratch, never `decodeParallel`. / Reason: W workers then use exactly W cores (no nested parallelism, no oversubscription) and inflate runs in parallel for free. P2.9's 45.6 ms at n=0 was one frame on 8 cores; single-core is about 1.7x that (52.4 vs 30.8 ms at (2,5)), so about 78 ms at n=0, and 6 workers give about 77 fps in theory. / Risk: memory bandwidth on the Air may cap scaling; measured with `--bench --workers`.
- P3-D2: Order and memory: results keyed by frame index; the consumer's request k sets a window [k, k + capacity) and workers only take indices inside it; a request outside the window restarts at k (generation counter discards stale work). Capacity = frames fitting in 1/4 of the heap, clamped to [2, max(8, workers)]: 8 at 1080p with -Xmx4g (about 200 MB). / Reason: H3 bounded buffer, at most capacity + workers frames alive. / Risk: step back by one restarts the window; FrameCache (P3.2) covers that.
- P3-D3: Hidden `mydecoder in.cmp --bench [--workers 1,2,6]` pulled forward from P3.6 so pipeline fps at n=0 can be proven on the Mac before the player is built. Off by default; spec CLI unchanged.
- P3-D4: [C/P3] `FrameCache`: ring of the last 30 frames the player requested, stored packed 0xRRGGBB (one int per pixel) plus the 8x8 type map; oldest inserted is evicted and its buffer reused; a miss is decoded through `DecodePipeline` (footer offset, random access) and inserted. / Packed is 1/3 of three int planes: 30 x 1080p = 249.8 MB instead of about 750 MB; reusing buffers avoids an 8 MB allocation per step. Single-threaded (player thread only). / Each step back beyond the ring restarts the pipeline window, decoding up to 8 frames of which only one is used; acceptable for occasional long step-backs, revisit if stepping feels slow in P3.3.
- P3-D5: [C/P3] `Player` on the main thread: deadline of frame i = t0 + (i - i0) * period (index-based, re-anchored on resume); when a frame is due it shows the NEWEST due frame (target = i0 + floor((now - t0)/period)), counting skipped ones as dropped; the target is always shown even if late; late = painted more than half a period after its deadline. Report printed at the end of the first uninterrupted pass: duration vs clip, dropped, late, mean decode wait, first and last 100 frames (shown, dropped, late, fps). Timing logic mirrors frozen `Clock` because its fake-time hook is package-private. / Holds the original rate (03 D8) and always moves forward; testable on a fake clock. / A frame can be up to one decode latency stale; the half-period late threshold matches P0's ProbeVideo report so numbers compare.
- P3-D6: [C/P3] `Display` (now Window C's): `show(int[] rgb, w, h)` for packed frames via `Scaler.applyPacked` (bit-identical to the plane path, tested) and `setStatus(text)` drawn over the picture on the event thread. `show(Frame)` unchanged, so `ProbeVideo --play` is unaffected. Hidden `mydecoder in.cmp --workers N` for the 4 vs 6 comparison. / The cache stores packed frames, so no unpacking per paint. / none.
- P3-D7: [C/P3] Pre-roll: the player shows frame 0, waits until frames 1..6 are decoded or 1 s passes, then anchors the clock with frame 0 counted as shown at t0. / Mac run 1 showed ~0.6 s of start-up counted as lag (19 frames dropped, durations 9 to 17% short). / Start is up to 1 s later; frame 0 sits on screen during pre-roll.
- P3-D8: [C/P3] Default decode workers changed from max(2, cores-2) = 6 to max(2, min(cores-2, cores/2)) = 4 on the Mac. Supersedes the default in P3-D1 (the frame-parallel design is unchanged). / Mac playback runs 1 and 2: at 1080p, 6 workers gave 27 to 45% late frames vs 8 to 12% with 4, both with zero or near-zero drops; bench shows 4 workers decode at 40.7 fps at (0,0) and 60.7 fps at (2,5), above 30. / At (0,0), 4 workers leave less decode margin (1.36x real time vs 1.59x); thermal behaviour checked in P3.7.
- P3-D8 confirmed Nov 12 by Mac run 4 (fair order 4,6,6,4): 4 workers 3.5% late on average vs 5.75% for 6, both 0 drops (RESULTS P3.3 run 4). Default stays max(2, min(cores-2, cores/2)).
- [A/P1] P1-D5: Hierarchical search parameters live in `MotionEstimator.HierParams` (levels 3, coarse +/-8, refine +/-2, lambda 4), not in `Config` / `Config` is frozen read-only since Nov 12 / two places hold thresholds until PM decides (PARCEL).
- [A/P1] P1-D6: Keep the 3 best coarse candidates and refine each to full resolution / a single coarse winner was a local minimum on fine textures; SAL agreement 89.0% to 89.8%, video2 93.4% to 95.8% / about 1.8x slower (sandbox 109 to 193 ms per 1080p frame).
- [A/P1] P1-D7: Final +/-1 polish at full resolution around the winning candidate / candidates (neighbours, previous frame, camera) can land 1 px off; SAL 87.3% to 89.0% / 9 extra SADs per block.
- [A/P1] P1-D8: Hierarchical search runs blocks in scan order on one thread / the median predictor needs the left, top and top-right results, and scan order keeps output deterministic / parallel version would need a wavefront; revisit only if the Mac misses the 200 ms target.
- [A/P1] P1-D9: Agreement metric counts textured blocks only (variance >= 100) and also reports "worse by >10%" / flat blocks have no single right answer, and on repeating textures an equally good alternative is not an error / the 90% figure alone overstates real misses on SAL.
- [A/P1] P1-D10: Reliable = Y variance >= 100 and MAD_best <= 12, in `Segmenter.SegConfig` / flat blocks match many positions and badly matched blocks did not find themselves (occlusion, blur); reliable share 31.4% (video1) to 68.5% (SAL) / starting values, tuned on all 4 clips in P1.9.
- P3-D9: [C/P3] View keys s (side by side), z (1:1 zoom), d (foreground overlay) and mouse drag (pan) are handled inside `Display` on the event thread, not by the Player: they only change how the current picture is drawn, and must work while paused. View logic is a pure nested class `Display.View` (fit, side by side, 1:1 crop with clamped pan, red tint at 3/8) tested without a screen. With an original, the window is two frames wide; single view is centered in it. In 1:1 side by side both halves show the same region. / Decoder and original line up pixel for pixel; scaled 1080p hides the artifacts the grader must compare (03 D8). / The arrays shown are re-read on a view key, so callers keep them alive until the next frame (both 30-frame rings do).
- P3-D10: [C/P3] Original mp4 for side by side read by `DecoderMain.OriginalVideo` (nested, to stay inside H3 file ownership): VideoIO forward reads in step with the player, 30-frame packed ring, reopen and reread from frame 0 on a step back past the ring; size checked against the .cmp before any window opens. Read on the player thread, so timing runs are made without the original. / Simple and correct; reading is ~6 ms per 1080p frame. / Long step-backs near the end of SAL reread a few seconds; a separate file would be cleaner (PARCEL).
- P3-D11: [C/P3] P3.4b: during pre-roll the player repaints frame 0 `WARM_PAINTS` = 15 times (not counted as paints) before starting the clock, so the scale and paint code is JIT-compiled before frame 1 is due. / Mac run 4: late frames clustered in frames 7 to 62 (first 2 s); goal whole-clip late under 2%. / About 150 ms more start-up; effect to be measured on the Mac (queued).
- P3-D12: [C/P3] P3.6: `DecoderMain.main` only calls `run(argv, err)` and exits with its code: 0 ok; 2 bad command line (usage printed; includes missing file and a non-number after --workers); 1 bad file or machine (not a .cmp, short file, wrong version, unfinished file, truncated/corrupt, original is a different video, no screen). One `error:` line each, all before any window opens. Usage text lists the view keys. / Testable without exiting the JVM or opening a window. / none.
- P3-D10 update (Nov 13, PM approved, P3.5c): `OriginalVideo` moved from a nested class in DecoderMain to its own package-private file `codec/decoder/OriginalVideo.java`; no behaviour change (168/168).
- [A/P1] PM answers Nov 13: P1-D5 accepted (thresholds stay in `HierParams` / `SegConfig` / `GmConfig`, `Config` stays frozen); SAL 89.8% agreement accepted with real misses reported beside it; VizSeg `--at` instead of `--frames a:b` accepted; piping frames to ffmpeg for a debug overlay mp4 allowed (00 section 4).
- [A/P1] P1-D11: Camera model fitted by hand-written RANSAC on reliable blocks only: homography (Hartley-normalized DLT, Gaussian elimination with partial pivoting), 500 iterations, seed 576, inlier distance 2.5 px, two least-squares refits on inliers; fallback to affine, then translation, when inliers < 30% / outliers (people, noise) must not pull the fit, and a fixed seed keeps labels identical run to run / 500 fixed iterations cost 1.5 to 10 ms per frame (sandbox) and could in theory miss a model with very few inliers; mean ratios 0.74 to 0.90 say that does not happen on our clips.
- [A/P1] P1-D12: A fit is "ill-conditioned" if it maps any frame corner behind the camera, moves it more than 20% of the larger frame side, or mirrors the image; such samples are skipped and such refits refused / a homography from 4 nearby points can extrapolate wildly at the frame edges / a camera that truly moves more than 384 px per frame at 1080p would be rejected (none of ours exceed 32 px).
- [A/P1] P1-D13: Fewer than 8 reliable blocks: median translation; no reliable blocks: camera assumed still (identity) / a homography from a handful of points is meaningless / such frames will lean on the temporal vote (P1.8).
- [A/P1] P1-D14: Naive baseline = textured (variance >= 100) and residual > 3 px, 4-connected groups >= 4 blocks, same vectors and same camera model as the real method / same-code baseline isolates what P1.6 to P1.8 add / it uses our better camera model, so the baseline is slightly stronger than doc 05's prototype.
- P3-D13: [C/P3] P3.4c (PM approved Nov 13): `OriginalVideo` reads the mp4 on its own thread, keeping up to AHEAD = 8 frames ahead of the latest request and BEHIND = 30 behind (at most 39 packed frames, about 320 MB at 1080p); a step back past the kept frames restarts the mp4 from frame 0 and keeps only frames near the target; evicted buffers are recycled, a restart drops frames without recycling so a frame still on screen is never overwritten. / Mac Nov 13: reading on the player thread dropped 13 to 45% of frames with the original open. / Memory up by about 70 MB vs the first version; re-measure on a quiet Mac.
- [A/P1] P1-D15: Region growing with a pairwise consistency rule (residuals within 2 px, or both >= 4 px and within 30 degrees), regions >= max(4, 0.2% of blocks) / implements B7 "contiguous and consistent in direction"; random-direction alias patches fall apart / chance chains of a few aligned noise blocks can survive (unit test allows < 15% of a random patch).
- [A/P1] P1-D16: Foreground candidates use a looser gate than the camera fit: MAD <= 12 and texture >= 20 (camera fit keeps texture >= 100) / walkers wear flat clothing; lambda already gives flat blocks their neighbours' vectors, so their residual is meaningful (Stairs f173 walker 0 -> 222 blocks) / more noise candidates, filtered by consistency and the camera test.
- [A/P1] P1-D17: Region spread is robust (median distance from the component-wise median residual), cap 3 px / RMS spread let a few wild limb vectors reject a whole walker; legs and torso move at different speeds (SAL f218 walker kept only at 3 px) / a noise patch with a coherent majority can pass.
- [A/P1] P1-D18: Camera-explained test: a block whose best SAD within 1 px of the rounded camera vector is at most max(1.0 x 256, 15% of its best SAD) above its own best SAD is background / coherent brick aliases match the camera's vector as well as their own (SAL f218 5.6% -> 3.7%) / a slow-moving object on a repeating texture could be called background; costs 9 SADs per block.
- [A/P1] P1-D19: Camera-explained test window is a parameter (`SegConfig.camWindow`, default 1 = 3x3 around the rounded camera vector) / added to test whether the window hid the slow Stairs f69 walker; window 0 recovers 0.6% of that frame but nearly doubles video2 false foreground / Stairs f69 accepted as a known limit (RESULTS "P1.6 known limit").
- [A/P1] P1-D20: P1.7 fill = 3-of-4 neighbour vote (on a copy, scan-order independent) + hole fill (pocket off the border, one bordering region, pocket <= region size); dilation implemented but off / closes holes inside people (Stairs f173 torso solid) for +0 to 0.6 points of foreground; dilation doubled foreground on all clips / dark flat trousers stay background.
- [A/P1] P1-D21: Temporal vote 2 of (t-1, t, t+1) with neighbours read through motion (t-1 at p + mv_t(p), t+1 at p - mv_{t+1}(p)); a missing neighbour at the clip ends counts as a copy of frame t; one frame of lookahead, streamed (`Segmenter.Temporal`, `Segmenter.Run`) / the camera moves up to 2 blocks per frame on video2, so same-grid voting would erase or ghost movers; flicker removed (16 to 22% of foreground on 3 clips) / the forward lookup is an approximation of the inverse vector; ends of the clip are not smoothed.
- [A/P1] P1-D22: Region ids are not matched across frames / block_type in the .cmp is binary (D7), so ids only change VizSeg colours / overlay colours can change between frames.
- [A/P1] P1-D23: P1.9 step 1: camSlackMad 1.0 -> 2.0 (camera-explained slack 2 grey levels per pixel) / best single change in the 4-clip sweep (SAL 2.01 -> 1.25, video2 6.79 -> 5.81 mean % on sweep frames) and people kept on whole-clip eye check / SAL loses the walker at the right edge in frames 409 to 427; Stairs 13 more empty frames, mostly the distant-walker stretch. Rejected: min region 8 blocks (erased small joggers and the skateboarder).
- P3-D14: [C/P3] Flaky OriginalVideoTest fixed (reported by Window A, 1 in about 12 runs, "expected 1 but was 2" reopens): the reader advanced `next` when it CLAIMED a frame, before packing and storing it, so a request for that exact frame during packing looked like a dropped frame and restarted the mp4. Now `next` advances only when the frame is stored (or deliberately skipped). Regression test holds the reader inside that window with a test hook (`afterClaim`) and checks no restart. / 20 of 20 repeated runs of OriginalVideoTest green. / none.

Golden SHA test pins the baseline payload and file bytes (computed before any P4 code). / Lossless, frames stay independent so the P3 player is unchanged. / Gain on checkerboard test files only 1.18x to 1.23x; myencoder option waits for wire-up (EncoderMain is Window A's).

- [A/P1] P1-D24: Optional parallax filter (`parallaxDeg`, `parallaxMinCam` = 4 px) built and tested, default OFF / at 30 degrees it removes the largest false-foreground class on video2 (6.95% -> 4.15% whole clip) and SAL's last brick patch / it also deletes real movers whose motion runs along the camera's flow, against 03 D3's "lean foreground when unsure"; DECISION REQUEST pending.

- P3-D16: [C/P3.R] Player keys moved from a frame KeyListener to root-pane key bindings (WHEN_IN_FOCUSED_WINDOW, plain and Shift), picture unfocusable; every view key (s, z, d) prints "view : <key> -> <state>" and the status bar says "side by side needs the original .mp4" when no original was given. / Dhruvin: s never splits on the Mac; Xvfb robot test: click on picture then s splits (6000 px of original), s again unsplits, q quits; 234/234. / Mac recheck pending.
- P4-D2: [C/P4] Mode 2 (P4-A, PM approved option A Nov 14; GOP 2 PM decision Nov 15): residual = frame minus motion-compensated prediction from the reconstructed previous frame, one vector per macroblock (2 signed bytes), DCT + 2^n1/2^n2 by block type + zigzag RLE (mode 1 body) + zlib; I frame every 2 (McCodec.GOP); GopPipeline decodes groups in parallel, plain ./mydecoder plays it; tool `McEncode` (3 threads, byte-identical to 1 thread). / All 4 clips at (2,5): 36 to 51% smaller than baseline within 0.23 dB (RESULTS "P4 final"); GOP sweep (P4-L3). / ./myencoder has no `--mode mc` (EncoderMain is Window A's; not added before freeze): mode 2 files come from `codec.tools.McEncode`.
